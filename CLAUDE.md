# 5eGoldBox

A layered C#/.NET 8 D&D 5e engine: `FiveEGoldBox.Core` (pure rules), `FiveEGoldBox.Application` (session/campaign orchestration, three scenarios: "Watchtower", a minimal "Sunken Chapel" that exists to prove the content boundary, and "The Hollow Mill" — the first authored to be worth playing rather than to prove a seam), `FiveEGoldBox.Console` (working text client), `FiveEGoldBox.Godot` (a real, backend-wired desktop client — outpost decisions, exploration (a real first-person 3D dungeon view plus a top-down bearings map), regional travel, tactical combat, and spellcasting are all playable against the actual engine, not mocks — see "Where things stand" just below for how it got there and what's still open).

## Where things stand (2026-08-02) — read this first if you're resuming cold

**Subclasses added — identity only, deliberately no mechanics, 2026-08-05.** The user asked directly whether this would be a pain; the honest answer turned out to be no, for a specific reason worth recording: real 5e picks a subclass above level 1 for three of this ruleset's four classes (Cleric at 1st, Wizard at 2nd, Fighter and Rogue at 3rd), and this engine has no leveling system at all — the exact same wall Extra Attack already hit ("indefinitely out of reach until leveling itself is built"). Presented that split to the user and they chose identity-only for all 8 subclasses over also building Cleric's real level-1 mechanics (Disciple of Life, War Priest), which would have meant extending the feature system to grant spells/resources, not just roll modifiers — a real, separate scoping question, left alone.

- **New `SubclassDefinition`** (`Core.Definitions`, Id/Name only, no mechanical fields — its own doc comment explains why one would describe something that can't happen yet). `ClassDefinition` gained `Subclasses`. Copies the already-working Race→Subrace pattern almost exactly, with one deliberate divergence: `CharacterDraft.SubclassId` is **always optional**, never required-when-available the way `SubraceId` is, since a level-1 character of a class that doesn't choose until later legitimately hasn't chosen one yet. `ValidateSubclassSelection` (new) only checks that a chosen subclass is real and belongs to the character's own class. `CharacterSnapshot` gained `SubclassId`/`SubclassName`, resolved in `CharacterResolver.Resolve` exactly where `RaceName`/`ClassName` already are.
- **A real trap found before it caused a silent bug:** the JSON Schema and actual content loading don't read `Core.Definitions` directly — they go through a separate versioned `Content/V1` DTO layer (`ClassDefinitionV1`, mapped by `RulesetPackMapper`) that mirrors Core's shape by hand. Adding `Subclasses` to `ClassDefinition` alone left the schema regeneration producing zero change and the hand-authored JSON content silently ignored (unmapped JSON properties are dropped, not rejected) — caught by checking the regenerated schema actually contained "Subclass" before moving on, not assumed. `SubclassDefinitionV1` + a `ToRuntimeSubclass` mapper closed the gap.
- **Content:** all 8 real subclasses authored in `data/rulesets/campaign/core.json` — Champion/Battle Master (Fighter), Thief/Arcane Trickster (Rogue), Life Domain/War Domain (Cleric), School of Evocation/School of Abjuration (Wizard). Schema regenerated via the documented `ContentPackSchemaWriter` un-skip/run/re-skip process.
- **`PartyMemberViewModel` gained `SubclassDisplayName`** (nullable), populated in `SessionView.DescribePartyMember` from `CharacterSnapshot.SubclassName` — the same engine-side "character sheet" surface `CharacterCreationRules` work already established, verified through `SessionView.Describe` in tests; no Godot rendering touched, matching that work's own "backend first" boundary.
- Public API: `Core.dll` 176 → 177 (one new type, `SubclassDefinition`; `ClassDefinition`/`CharacterDraft`/`CharacterSnapshot` gained members, not new types). `Application.dll` held at 76 (`SubclassDefinitionV1` is internal; `PartyMemberViewModel` gained a member). Full solution gate green (Debug+Release, 0 warnings; 2333 tests, +13 new — 9 Core, 4 Application — the rest unaffected including the frozen combat transcripts); Godot build 0 warnings (untouched). **Verified against real content, not just synthetic fixtures:** a Cleric built through `CharacterCreationRules` with `SubclassId = "subclass.war-domain"` starts a real Hollow Mill session and shows "War Domain" on its resolved character sheet; a subclass belonging to a different class (Fighter's own subclass on a Cleric draft) is correctly rejected with `character.subclass.not_found`.
- **Explicitly not done, and not currently planned:** any live mechanical effect for any subclass. Revisit only alongside a real leveling-system scoping pass — building it sooner would be mechanics with no content that could ever need them, the same call already made for Extra Attack.

**Character-creation backend built (engine-only, no UI), 2026-08-05 — the first piece of the accepted Scope Matrix's §6.2 "Campaign Character Creation."** The Scope Matrix (`docs/5e Gold Box Supported Scope Matrix.docx`) is explicit that the current technical slice has "Character creation UI: None" by design (every party member is a fixed, campaign-authored roster entry) and that real player-driven creation belongs to the first-campaign milestone, not this one — this is backend plumbing built ahead of that milestone, at the user's request, with zero Godot/UI work.

- **The real blocker wasn't a missing facade, it was two places that hard-require a roster match.** `CampaignPartyCompositionValidator` re-validates every party member against `CampaignDefinition.Roster` on *every single session mutation* (it's called from `ApplicationSessionRules.CreateCanonical`, the universal re-validation gate every rule in the engine routes through), and `CampaignCharacterDraftFactory.CreateDraft` re-derives a member's full build from that same roster lookup every time combat or the character sheet needs real stats. A player-created character has no roster entry, so both would reject it outright. Found by reading the actual call graph before writing anything, not assumed.
- **`PartyMemberState` gained one new field, `CustomBuild: CharacterDraft?`** — reusing Core's existing, already-public `CharacterDraft` type rather than inventing a parallel one. Null for every roster character; populated for one `CharacterCreationRules` built. `CampaignCharacterDraftFactory.CreateDraft` now returns it directly (merged with the member's live ammunition state) when present, instead of requiring a roster lookup. `CampaignPartyCompositionValidator.ValidateMember` gained a parallel custom-build branch that re-derives expected class/max-HP/resources/ammunition by resolving the build through `CharacterResolver` (the same pipeline every other consumer already uses) instead of reading a `CampaignCharacterDefinition`. `CampaignResourceGrants.ForCharacter(campaign, character)` was generalized to `ForClass(rulesetId, classId)` so both paths share the one place that answers "what does this class grant" rather than duplicating it.
- **New public `CharacterCreationRules`** (`Application/Characters/`): `Validate(CharacterDraft, rulesetId)` and `CreateParty(partyId, IReadOnlyList<CharacterCreationEntry>, rulesetId)`, built on the exact `CharacterResolver`/`PointBuyRules`/`StandardArrayRules` pipeline that already existed, fully tested, with zero callers before this — the same shape of unused scaffolding the reactions system turned out to be. Deliberately narrower than what `CharacterDraft` as a shape allows: `CheckCreationScope` rejects anything above level 1 and anything using `Manual`/`Rolled` ability generation (`Manual` has no fairness constraint at all — it's how the fixed roster bakes its numbers directly), matching the Scope Matrix's actual commitment (level 1 only; standard array or point buy; random rolling deferred) rather than the wider set Core's validation alone would allow.
- **`ScenarioSessionFactory` gained a `CreateNew(scenarioId, randomSeed, PartyState)` overload** so a `CharacterCreationRules`-built party can actually start and play a real session, not just sit as an inert object — `ApplicationSessionRules.CreateNew` already accepted an arbitrary `PartyState`, so this was additive, not a rework.
- **Save format:** `SavePartyMemberV1` gained an optional `CustomBuild: SaveCharacterDraftV1?` (new DTO, plus small enum-wrapper types for `Ability` and `AbilityScoreGenerationMethod`, matching every other enum in this file's own convention of never serializing a Core enum directly), defaulting to null so every pre-existing save fixture still loads unchanged. Skipping this was considered and rejected — without it, a custom-built party would silently lose its build the moment it saved and reloaded, since nothing else in the engine can reconstruct a character's build from nothing.
- **Explicitly not done:** any Godot/UI work; subclasses (no `SubclassDefinition` concept exists anywhere in Core — confirmed by direct search — a real, separate scoping question, since 8 are needed for the campaign spec and today there are zero); new race/background content (only Human/Soldier exist today; the campaign spec needs 4 species with 7 race/subrace combinations and 4 backgrounds) — the pipeline was proved end-to-end using only currently-authored content, on purpose, so content authoring is a separate follow-up rather than blocking the mechanism.
- Public API: `Application.dll` 74 → 76 (two new types — `CharacterCreationRules`, `CharacterCreationEntry` — everything else added members to already-public types, reflection-verified). Full solution gate green (Debug+Release, 0 warnings; 2320 tests, +12 new — `CharacterCreationRulesTests` — the rest unaffected, including the frozen combat transcripts); Godot build 0 warnings (Godot-side code untouched, confirmed unaffected since `Application`'s public surface only grew). **Verified end-to-end, not just unit-level:** a real 4-character custom party (Human Fighters, standard-array scores, real equipment) built through `CharacterCreationRules.CreateParty` actually starts a real Hollow Mill session via `ScenarioSessionFactory`, passes real canonicalization, resolves a real character sheet through `SessionView.Describe` (race/class/level/AC/all six ability scores), and survives a full save/load round trip with its build intact — all against the real shipped `ruleset.campaign` content, not a synthetic test fixture.

**Gold Box overland travel design reference analyzed, 2026-08-04 — read `docs/2026-08-04-gold-box-overland-travel-gap-analysis.md` before picking up regional-travel work.** The user supplied a 28-section design spec (same Pool of Radiance/Gateway/Treasures/FRUA lineage as the combat doc) for a Gold Box-style overland travel engine. Same method as the combat analysis: a dedicated investigation pass read the actual travel implementation file-by-file (`RegionalTravelRules.cs`, `RegionalTravelState.cs`, `TravelRouteDefinition.cs`, all three scenarios' route data) rather than trusting memory — full file:line citations are in the doc itself.

**Verdict: much thinner than combat was.** Combat had a solid, tested foundation with nameable gaps on top. Regional travel is a genuinely minimal placeholder — a named route walked in a fixed number of clicks (`CurrentStepIndex` → `FinalStepIndex`), fully deterministic (confirmed: zero RNG usage anywhere in the `Travel` folder), with no time, no risk, and nothing that can happen mid-journey. **Every actual danger and scripted event in this engine today happens after arrival, during exploration — regional travel itself can never produce an encounter.** What's already correct: the pure-C#/deterministic/headless-testable domain shape (same discipline as everywhere else in this engine), the route-graph model (correctly *not* a Pool-style cell grid — the doc itself endorses the Gateway/Treasures location-to-location school this already uses), real multi-route player choice (Hollow Mill's two routes from one origin), and progress-gated route open/closed state re-validated on every step.

**The one foundational gap, bigger than travel itself: no campaign clock exists anywhere in this engine.** Not stubbed, not travel-scoped — there is no `CampaignTime`/day-night/calendar concept in `Core` or `Application` at all, confirmed by direct search. This is the doc's single most load-bearing requirement (spell durations, rest, and any future deadline/shop-hours content all sit downstream of it too), and it's the real prerequisite decision the same way stepwise movement was for combat's reactions gap.

**Real gaps, tiered in the doc:**
- **Self-contained, buildable once (or partly before) a clock exists:** travel can never be interrupted — no encounters, no discoveries, no events of any kind mid-route; no interruption/stop-condition policy exists because nothing can currently trigger one; route cost is step-count only, no terrain/weather/pace/mode effect on duration.
- **Larger, content-gated (matches this project's own stated "mechanics only where content demands" philosophy):** travel modes (boats/mounts/passenger routes — zero infrastructure today), location visibility states beyond binary open/closed (Unknown/Rumored/Revealed/Closed/Destroyed/Expired), zones (regional encounter/combat-backdrop selection), rest/encamp during travel (not travel-specific — `Encamp` doesn't exist for real sessions anywhere in this engine today, mock-only), deadlines and scheduled world events.

**Combat camera: turn-change recentering replaces the competing focus-edge force (2026-08-04).** Found live, at the office, right after the medieval-heroes/apex-predators/floor-tile art from the entry above finally rendered (a separate, already-fixed local `.godot` import-cache issue, not this bug — see the "Verifying Godot-side work" section below): on an 8×8 real battlefield (genuinely bigger than the viewport now, per the "Uniform combat floor" work above), mouse-hover edge-scrolling would move "a fraction of an inch and stop," and nothing ever recentered on whoever's turn it was after the encounter's opening moment. Root cause was two forces fighting: `ApplyEdgeAutoScroll` summed the mouse-hover term with a second, continuous per-frame term pulling to keep the *active* combatant within `FocusEdgeDeadzoneTiles` of every edge — the moment a mouse-driven scroll moved the active combatant's own screen position toward that deadzone from the other side, the two terms canceled. Separately, only `Configure` (a fresh encounter) ever called `CenterPanOnFocus`; an ordinary `Refresh` (every turn advance) only clamped, never recentered, so "center on whoever has initiative" only ever happened once, at the very start.
- Fixed by replacing both with one rule: `CombatView.cs`'s `Refresh` now tracks `_lastCenteredCombatantId` and calls `CenterPanOnFocus` exactly when `ActiveCombatantId` changes from what it last centered on — a turn advance recenters, a target selection or a move that doesn't end the turn doesn't (matching "center on whoever's turn it is," not "yank the camera on every highlight change," which is what the user actually asked for). `Configure` now just resets that tracked ID to null before calling `Refresh`, so a fresh encounter's opening turn goes through the exact same recenter path rather than a separate explicit call — one mechanism, not two.
- `ApplyEdgeAutoScroll` (`CombatView.Zoom.cs`) dropped the focus-tracking term entirely — mouse-hover is now the only thing driving continuous per-frame scrolling, uncontested by anything else pulling toward a different point. `FocusEdgeDeadzoneTiles` and its associated comments were removed with it.

**Combat camera, the actual fix: `SetPanOffset`'s clamp couldn't pan in the positive direction at all (2026-08-04, same day).** The turn-centering fix above was real but didn't touch the actual bug — confirmed live, twice: first a rebuild-didn't-happen false lead (`godot --path` run mode doesn't recompile changed C#, see "Verifying Godot-side work" below, a real separate finding from the same debugging session), then a genuine "still broken after an actual rebuild" report that needed real data, not another guess. Added a small always-on debug label to `CombatView` (`%DebugCameraLabel`, mirroring `AreaMapView`'s own `(X, Y) Facing` overlay) showing the active combatant, computed focus point, and current pan offset — and the very first screenshot with it running showed `focus=(277.76, -38.08)` against a `(714, 400)` viewport, which wants a desired pan of roughly `(+79, +238)` to center it, but `pan=(0, 0)`. Root cause: `SetPanOffset`'s clamp was hardcoded to `Mathf.Clamp(desired, minOffset, 0)` — an upper bound fixed at exactly zero, meaning pan could only ever go negative or stay at zero, never positive. That was a correct assumption back when a diamond always fit inside the background image and panning only ever needed to reveal more toward the bottom-right; it silently broke the moment `ReferenceSpan` (see the "Uniform combat floor" entry above) started centering a diamond *bigger* than the image, which pushes real tiles into negative content-local coordinates on the diamond's own top-left — content the old clamp could never pan far enough right/down to reach, no matter what `CenterPanOnFocus` asked for. Concretely, the party's own starting corner sat 38px above the viewport's top edge, permanently, on every encounter, from the very first frame — this was never actually about turn-change timing at all.
- Fixed by computing the diamond's real bounding box from `Project`'s own extremes (leftmost at grid `(0, gridHeight)`, rightmost at `(gridWidth, 0)`, topmost at `(0, 0)`, bottommost at `(gridWidth, gridHeight)` — not derived from `DiamondWidth`/`DiamondHeight` alone, which are only symmetric around `OffsetX` for a square grid), unioned with the background image's own rect, and clamping against that union's actual min/max on each axis instead of a hardcoded `[min, 0]`. Verified by hand against the exact numbers the debug overlay reported before shipping: the same focus point now clamps to a pan of `(79, 117)` (the fully-centering `238` on Y gets clamped short, correctly, since the diamond genuinely doesn't extend far enough up to reach dead-center without exposing empty space beyond it) — putting that same point at screen Y≈79 inside a 400px-tall viewport, not −38 off the top edge.
- The debug overlay itself (`%DebugCameraLabel`) is left in the shipped view rather than stripped out, on the same "cheap and worth keeping" reasoning `AreaMapView`'s facing overlay was kept for.
- Verified: Godot build 0 warnings, headless boot exit 0 empty stderr, main solution unaffected. **Still needs the user's own eyes** — the debug-overlay numbers prove the math now produces a real, bounded, non-zero pan where it used to produce exactly zero, but nothing here has confirmed the on-screen feel yet.

## Workflow authorization for branch work in this repo

**Standing authorization (confirmed 2026-07-30, extended from this section's original Priority-1-only scope to general engineering work in this repo).** For a narrowly-scoped implementation task — a bug fix, a decided refactor, a plan-doc line item — proceed autonomously through the full loop without stopping to ask permission at each step, including the push/PR/merge:

1. Confirm `git status` clean and `main` in sync with `origin/main`.
2. One narrowly-scoped branch per concern.
3. Implement.
4. Gate: focused tests → full affected-project tests → full solution build+test (Debug and Release, both 0 warnings) → `git diff --check`. Also verify compiled public API counts via reflection (`Assembly.GetExportedTypes()`) when a change could affect visibility — don't trust grep or doc claims for this.
5. Self-review the diff; report gaps honestly rather than glossing over them.
6. Commit — one commit, message explains what and why. **If the change is worth a line in "Where things stand" (a shipped feature, a status change, a corrected claim, a moved test/API count), update CLAUDE.md in the same commit — not a separate follow-up chore.** This is a standing priority, not optional polish: PRs #211–227 shipped five real Phase 1 features without it, and the doc was stale again within a day of the 2026-08-02 truth pass that had just fixed exactly this problem. A CLAUDE.md update that rides along with the code that motivated it costs nothing extra; one done later as its own pass is the thing that keeps not happening.
7. `git add` **specific paths only, never `-A` or `.`** — the repo root has ~50 untracked process-doc/patch/log files (see below) that must never be staged. **`git stash -u` is the same hazard** and is equally off-limits: it lifts the untracked `docs/` assets out of the working tree, and that work is often being edited concurrently. If a clean tree is needed to build a baseline (e.g. the reflection API check against `main`), use `git worktree add` or a copy in a scratch directory instead of stashing.
8. Push, open a PR (`gh pr create`), wait for CI (`gh run watch`), merge (`gh pr merge --merge --delete-branch`) once green.
9. `git fetch --prune`, confirm `main` synced, move to the next branch (rebasing it onto the newly-merged `main` first if it was branched earlier in the same batch).

Still pause and flag rather than pushing through: gate failures, merge conflicts, CI failures, or anything that looks destructive/irreversible outside the normal branch→PR→merge flow. Still stop and ask first for anything that isn't a narrowly-scoped, already-decided task — genuine design/product decisions (see the "needs your decision" items tracked elsewhere in this file), force-pushes, history rewrites, or deleting/closing things outside the normal merge flow.

## Developer quick-reference: jumping straight to an exploration location

Both clients can start a session already inside a specific exploration location/floor/position/facing, bypassing the outpost decision and regional travel — for checking a spot on a map (a door, treasure, rendering) without replaying a scenario up to it every time. `ScenarioSessionFactory.CreateAtExploration` (`src/FiveEGoldBox.Application/Scenarios/ScenarioSessionFactory.cs`) is the shared engine seam behind both.

**Console — `goto` verb:**

```
dotnet run --project src/FiveEGoldBox.Console -- goto <scenario-id> <location-id> <floor> <x> <y> <facing> [progress-id]
```

Worked example, landing on the tile adjacent to Watchtower's armory door:

```
dotnet run --project src/FiveEGoldBox.Console -- goto scenario.watchtower location.ruined-watchtower GroundFloor 3 1 East MissionAccepted
```

**Godot — five (or seven) `FIVEEGOLDBOX_DEBUG_*` env vars**, same trusted-absolutely/fail-loudly convention as `FIVEEGOLDBOX_DATA_ROOT` above: `FIVEEGOLDBOX_DEBUG_LOCATION_ID`, `FIVEEGOLDBOX_DEBUG_FLOOR`, `FIVEEGOLDBOX_DEBUG_X`, `FIVEEGOLDBOX_DEBUG_Y`, `FIVEEGOLDBOX_DEBUG_FACING`, an optional `FIVEEGOLDBOX_DEBUG_PROGRESS_ID`, and an optional `FIVEEGOLDBOX_DEBUG_SCENARIO_ID` (added 2026-08-03 — `AppShell.CreateRealSession` hardcoded the debug path to `scenario.watchtower` regardless of which location was named, so pointing `LOCATION_ID` at a Hollow Mill/Sunken Chapel location threw `Scenario 'scenario.watchtower' has no location '...'`; defaults to `scenario.watchtower` when unset, so every example below and every pre-existing invocation is unaffected). Only `LOCATION_ID` gates the override — set it and floor/X/Y/facing become required, or the app fails loudly naming the missing one rather than silently booting to the outpost. Worked example, same spot:

```
FIVEEGOLDBOX_DEBUG_LOCATION_ID=location.ruined-watchtower FIVEEGOLDBOX_DEBUG_FLOOR=GroundFloor FIVEEGOLDBOX_DEBUG_X=3 FIVEEGOLDBOX_DEBUG_Y=1 FIVEEGOLDBOX_DEBUG_FACING=East FIVEEGOLDBOX_DEBUG_PROGRESS_ID=MissionAccepted godot --path src/FiveEGoldBox.Godot
```

Worked example needing the new override — Hollow Mill's upper floor, one tile from the mill-vermin-swarm trigger (walk east into it to fight two mill-rats):

```
FIVEEGOLDBOX_DEBUG_SCENARIO_ID=scenario.hollow-mill FIVEEGOLDBOX_DEBUG_LOCATION_ID=location.hollow-mill-house FIVEEGOLDBOX_DEBUG_FLOOR=UpperFloor FIVEEGOLDBOX_DEBUG_X=2 FIVEEGOLDBOX_DEBUG_Y=0 FIVEEGOLDBOX_DEBUG_FACING=East FIVEEGOLDBOX_DEBUG_PROGRESS_ID=mill.herbalist-consulted godot --path src/FiveEGoldBox.Godot
```
