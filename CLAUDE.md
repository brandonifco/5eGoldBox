# 5eGoldBox

A layered C#/.NET 8 D&D 5e engine: `FiveEGoldBox.Core` (pure rules), `FiveEGoldBox.Application` (session/campaign orchestration, three scenarios: "Watchtower", a minimal "Sunken Chapel" that exists to prove the content boundary, and "The Hollow Mill" — the first authored to be worth playing rather than to prove a seam), `FiveEGoldBox.Console` (working text client), `FiveEGoldBox.Godot` (a real, backend-wired desktop client — outpost decisions, exploration, regional travel, tactical combat, spellcasting, and a real top-down area map are all playable against the actual engine, not mocks — see "Where things stand" just below for how it got there and what's still open).

**Data-driven content — Phases 1–4 done, 2026-07-30.** All campaign/scenario/ruleset content stopped being hardcoded C# and became pluggable data a loader reads, per the user's stated 2026-07-28 long-term goal. `docs/archive/2026-08-02/2026-07-30-data-driven-content-plan.md` records the format/schema discussion (JSON; versioned DTOs + a mapper, mirroring the existing `Persistence/V1`/`SaveGameMapper` discipline exactly; flat `type.name` IDs with the loader failing loudly on any cross-pack collision; scenarios/campaigns stay one-file-per-adventure, pack-style merging reserved for ruleset content) and the four phases that followed it — ten PRs, #182–#195:

- **Phase 1 (PRs #182–186):** ruleset content (races, classes, backgrounds, skills, weapons, spells, effects, features, equipment) moved to `data/rulesets/campaign/core.json`. `Content/V1/` holds the versioned DTOs plus `RulesetPackMapper`/`RulesetPackLoader` — the latter also does real pack-merge (multiple files' lists unioned; `RulesetValidator`'s existing `ruleset.*.duplicate_id` checks catch a cross-pack collision for free, no new validation code needed). `CampaignRulesetContent.cs` and its three partials are gone; still-needed IDs moved to `CampaignRulesetIds`.
- **Phase 2 (PRs #188–190):** scenario content (Watchtower, Sunken Chapel, Hollow Mill — locations, exploration maps, routes, encounters, triggers, decisions) moved to `data/scenarios/*/scenario.json`. `WatchtowerScenarioDefinitionProvider`/`SunkenChapelScenarioDefinitionProvider`/`HollowMillScenarioDefinitionProvider` are gone; still-needed IDs moved to `SunkenChapelScenarioIds`/`HollowMillScenarioIds` (Watchtower needed none — its IDs already lived on separate classes).
- **Phase 3 (PRs #191–193):** the campaign roster (Fighter/Rogue/Cleric/Wizard active, Barbarian/Ranger reserve) moved to `data/campaigns/frontier/campaign.json`. `FrontierCampaignContent.cs` is gone; still-needed IDs moved to `FrontierCampaignIds`.
- **Phase 4 (PRs #194–195):** `DataDirectoryLocator` (the seam every loader above resolves a file path through) gained a `FIVEEGOLDBOX_DATA_ROOT` environment-variable override — trusted absolutely, fails loudly if the file isn't there — alongside the existing dev-checkout walk-up fallback. **Verified against the real Godot engine, not just Console/tests:** three real headless boots, one with no override, one with a deliberately wrong `FIVEEGOLDBOX_DATA_ROOT` (produced the exact expected failure), one with a correct one — all exit 0, zero-byte stderr, and `AppShell` builds a real session on every boot, so this is proof the data genuinely loads through Godot's own .NET runtime. Each phase's own equivalence test (comparing JSON-loaded content against the hardcoded C# it replaced, via a generic recursive structural comparer) is deleted once its cutover PR lands — the same discipline the frozen combat transcripts already established, and both transcripts passed unchanged at every phase boundary, including the final one where the whole roster switched from hardcoded C# to a JSON file. **Phase 5 (authoring ergonomics) — done, 2026-07-30, two PRs.** It had been flagged but not scoped in detail; scoping it turned up two independent deliverables, done as separate branches.

- **Standalone pack-validation command (PR #197).** `ContentPackValidation` is a new small public facade on `Application` (`Content/ContentPackValidation.cs`; public API 63 → 64, reflection-verified — one new type, nothing else) wrapping the existing internal loaders/validators for all three pack kinds and collecting every issue into a `ValidationResult` instead of throwing on the first one, matching `ScenarioDefinitionValidator`'s own stated philosophy ("loading refuses, tooling reports"). Console gained a `validate` verb: `dotnet run --project src/FiveEGoldBox.Console -- validate <ruleset|scenario|campaign> <path> [<path>...]` (ruleset supports multi-pack merge; scenario/campaign are single-file) — the first real need to justify Console's `Program.Main` taking arguments at all, flagged as "easy to add later" when the data-root override work (above) explicitly declined to add one speculatively.
- **JSON Schema for editor autocomplete (PR #198).** Rather than hand-author and maintain three schemas against ~60 DTO types, `JsonSchemaGenerator` (internal, `Content/Schema/`) derives a JSON Schema (2020-12) by reflecting over the V1 DTO graph itself — a C# `required` member becomes a schema `required` entry, `IReadOnlyList<T>`/`IReadOnlyDictionary<K,V>` become array/object, enums become string enums (matching the loaders' own `JsonStringEnumConverter(namingPolicy: null)`), so a schema can only go stale by a DTO changing without regenerating, not by drifting from hand-maintenance. `ContentPackSchemaWriter` (skipped by default, matching `FixtureWriter`'s own convention) regenerates `data/schemas/{ruleset,scenario,campaign}-pack.schema.json` on demand; `ContentPackSchemaTests` is the always-on drift check (regenerates in memory, diffs byte-for-byte against what's checked in) plus structural assertions (every `$ref` resolves, required lists match, enum values match). All five existing `data/**/*.json` content files gained a top-level `"$schema"` property pointing at the matching file — a VS Code/JetBrains-recognized convention for associating an instance document with a schema, not a JSON Schema keyword itself, which is why the generator explicitly allows `"$schema"` as an extra root-level property despite `additionalProperties: false` everywhere else. Verified the loaders tolerate the new field (they already ignore unmapped JSON members) via the full existing suite, unchanged. Public API held at 64 (everything added is internal).

- **Phase E (PR #200):** a new `import-map` Console verb converts a Tiled map editor JSON export (`.tmj`) into one location's `ExplorationMap` plus tile-anchored `Triggers`, merges it into an existing scenario file, and reports through the public `ContentPackValidation.ValidateScenarioPack` facade — the same "report, don't gatekeep" shape `validate` already uses. ## Workflow authorization for branch work in this repo

**Standing authorization (confirmed 2026-07-30, extended from this section's original Priority-1-only scope to general engineering work in this repo).** For a narrowly-scoped implementation task — a bug fix, a decided refactor, a plan-doc line item — proceed autonomously through the full loop without stopping to ask permission at each step, including the push/PR/merge:

1. Confirm `git status` clean and `main` in sync with `origin/main`.
2. One narrowly-scoped branch per concern.
3. Implement.
4. Gate: focused tests → full affected-project tests → full solution build+test (Debug and Release, both 0 warnings) → `git diff --check`. Also verify compiled public API counts via reflection (`Assembly.GetExportedTypes()`) when a change could affect visibility — don't trust grep or doc claims for this.
5. Self-review the diff; report gaps honestly rather than glossing over them.
6. Commit — one commit, message explains what and why. **If the change is worth a line in "Where things stand" (a shipped feature, a status change, a corrected claim, a moved test/API count), update CLAUDE.md in the same commit — not a separate follow-up chore.** This is a standing priority, not optional polish: PRs #211–227 shipped five real Phase 1 features without it, and the doc was stale again within a day of the 2026-08-02 truth pass that had just fixed exactly this problem. A CLAUDE.md update that rides along with the code that motivated it costs nothing extra; one done later as its own pass is the thing that keeps not happening.
7. `git add` **specific paths only, never `-A` or `.`** — the repo root has ~50 untracked process-doc/patch/log files (see below) that must never be staged. **`git stash -u` is the same hazard** and is equally off-limits: it lifts the untracked `docs/` assets out of the working tree, and that work is often being edited concurrently. If a clean tree is needed to build a baseline (e.g. the reflection API check against `main`), use `git worktree add` or a copy in a scratch directory instead of stashing.
8. Push, open a PR (`gh pr create`), wait for CI (`gh run watch`), merge (`gh pr merge --merge --delete-branch`) once green.
9. `git fetch --prune`, confirm `main` synced, move to the next branch (rebasing it onto the newly-merged `main` first if it was branched earlier in the same batch).

Still pause and flag rather than pushing through: gate failures, merge conflicts, CI failures, or anything that looks destructive/irreversible outside the normal branch→PR→merge flow. Still stop and ask first for anything that isn't a narrowly-scoped, already-decided task — genuine design/product decisions (see the "needs your decision" items tracked elsewhere in this file), force-pushes, history rewrites, or deleting/closing things outside the normal merge flow.

## Developer quick-reference: jumping straight to an exploration location

Both clients can start a session already inside a specific exploration location/floor/position/facing, bypassing the outpost decision and regional travel — for checking a spot on a map (a door, treasure, rendering) without replaying a scenario up to it every time. `ScenarioSessionFactory.CreateAtExploration` (`src/FiveEGoldBox.Application/Scenarios/ScenarioSessionFactory.cs`) is the shared engine seam behind both.

**Console — `goto` verb:**

```
dotnet run --project src/FiveEGoldBox.Console -- goto <scenario-id> <location-id> <floor> <x> <y> <facing> [progress-id]
```

Worked example, landing on the tile adjacent to Watchtower's armory door:

```
dotnet run --project src/FiveEGoldBox.Console -- goto scenario.watchtower location.ruined-watchtower GroundFloor 2 1 East MissionAccepted
```

**Godot — five (or six) `FIVEEGOLDBOX_DEBUG_*` env vars**, same trusted-absolutely/fail-loudly convention as `FIVEEGOLDBOX_DATA_ROOT` above: `FIVEEGOLDBOX_DEBUG_LOCATION_ID`, `FIVEEGOLDBOX_DEBUG_FLOOR`, `FIVEEGOLDBOX_DEBUG_X`, `FIVEEGOLDBOX_DEBUG_Y`, `FIVEEGOLDBOX_DEBUG_FACING`, and an optional `FIVEEGOLDBOX_DEBUG_PROGRESS_ID`. Only `LOCATION_ID` gates the override — set it and the other four become required, or the app fails loudly naming the missing one rather than silently booting to the outpost. Worked example, same spot:

```
FIVEEGOLDBOX_DEBUG_LOCATION_ID=location.ruined-watchtower FIVEEGOLDBOX_DEBUG_FLOOR=GroundFloor FIVEEGOLDBOX_DEBUG_X=2 FIVEEGOLDBOX_DEBUG_Y=1 FIVEEGOLDBOX_DEBUG_FACING=East FIVEEGOLDBOX_DEBUG_PROGRESS_ID=MissionAccepted godot --path src/FiveEGoldBox.Godot
```
