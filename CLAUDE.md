# 5eGoldBox

A layered C#/.NET 8 D&D 5e engine: `FiveEGoldBox.Core` (pure rules), `FiveEGoldBox.Application` (session/campaign orchestration, three scenarios: "Watchtower", a minimal "Sunken Chapel" that exists to prove the content boundary, and "The Hollow Mill" — the first authored to be worth playing rather than to prove a seam), `FiveEGoldBox.Console` (working text client), `FiveEGoldBox.Godot` (a real UI shell through M6e — input/focus framework, mock-driven scenario catalog, exploration/regional-map view scaffolding — merged back into this working tree 2026-07-28 after developing on its own `godot-ui` branch/worktree; still entirely decoupled from `Application`/`Core`, not yet wired — see "Repo hygiene" below).

## Current work: the Priority 1 Development Plan

It's an 8-phase sequence to stabilize the public API and persistence boundary before further scenario/orchestration refactors, executed as one small branch per phase step.

- [x] Phase 7 — Cross-layer die capability alignment. **Complete** (PRs #110–#111). The inventory found a real, latent misalignment: Core defines six dice, and `ApplicationRandomSequence.GenerateDie` accepted four. A weapon dealing **1d4 or 1d10** — a dagger, a heavy crossbow — passed Core's ruleset validation *and* Core's own `Enum.IsDefined` checks, then threw `ArgumentOutOfRangeException` partway through a fight at the moment its damage was rolled. Latent only by luck: the Watchtower's weapons are d6/d8/d12, and the `DieType.D10` in the live ruleset is a class *hit* die, which resolves through fixed averages and never reaches the random source.
  - **Root cause was two independent lists of numbers.** `GenerateDie` took a raw `int sides` with its own hardcoded set. It now takes a `DieType`, so there is one list and it is Core's. `ApplicationRandomSequence.IsSupported(DieType)` is the single answer to "can this be rolled".
  - **Determinism is preserved and proven.** The side count still goes into the hash and `DieType`'s values *are* the side counts, so the bytes hashed for a d20 are unchanged. Both frozen combat transcripts pass untouched, and the four vectors the test file already pinned (d6=1, d8=8, d12=9, d20=12) sit unchanged beside the new d4=2 and d10=9. Those new vectors were computed from an independent implementation of the documented algorithm that reproduces all four pre-existing ones — not read out of the code under test.
  - **Dice are now checked when content loads, not when it is rolled** (PR #111), in three places. Core rejects a weapon whose damage or versatile damage names a die outside `DieType` (the weapon validator checked damage type and properties but never the die). Core rejects a class hit die it cannot size hit points from (previously read for the first time during character resolution, throwing from inside `CharacterResolver`). And `ApplicationRulesetLoader` rejects a die Core accepts but the random sequence cannot produce — **Core cannot make that check itself, because it does not know Application exists**, which is why the two are separate. It catches nothing today; the point is the next die Core gains fails there until someone makes it rollable.
  - `HitDiceRules` holds the hit-die list so the resolver and the validator read one source. **Hit dice supporting only d6–d12 is 5e being 5e** — there is no d4 or d20 hit die — not a gap to close. Don't "align" it with `DieType`.
- [x] Phase 8 — Test infrastructure improvement. **Complete** (PRs #113–#114), and mostly a matter of finding out how little was actually warranted. The plan called it ongoing rather than a gate, and it had been: builders and per-behaviour test files accumulated across Phases 2–7.
  - **The headline duplication counts are misleading — measure bodies, not declarations.** `CreateEncounter` is declared in 10 Core test files but only 2 are identical; the other 8 have parameter lists shaped by the behaviour under test (cover, blocked squares, adjacent threat, roll modes). `CreateValidDraft` is declared in 39 files with **24 distinct bodies**. In both cases the variation *is* the setup each test cares about, so both were left alone — collapsing them behind shared defaults is the "general-purpose test language" the phase gate explicitly forbids. If you revisit this, re-measure distinct bodies before touching anything.
  - What was real: 30 byte-identical fixture declarations — `CreateHumanRace` ×10, `CreateLeatherArmor` ×7, `CreateShield` ×7, and one `CreateLongsword` variant ×6. `TestRulesetBuilder.HumanRace()` already existed and matched all ten copies character-for-character, so the shared definition was there and unused; builders had been introduced earlier but adoption stalled at 5 usages. `Longsword`/`LeatherArmor`/`Shield` joined the catalogue and the copies went (−594/+118 lines). A **second** `CreateLongsword` body in five other files was left in place: the rewrite only ran where the body hashed to the canonical one.
  - `EncounterRulesTests` (1837 lines, 40 `Start_*` + 17 `Complete_*`) split into `.Start.cs`/`.Complete.cs` plus a shared-fixture file, as a **partial class** — the convention `ConsoleSessionRunner.cs`/`.Combat.cs`/`.Noncombat.cs` already established. Helpers stayed inside the class so neither half lost visibility. Verified as pure motion by diffing the set of test-method names before and after.
  - **No other file needed splitting.** The Core suite is already 123 files divided by behaviour; the remaining large ones cover a single class's entry points thoroughly, which is cohesion, not sprawl.

- [~] Phase 10 — Mechanics in service of content. Attacks against a downed target now have advantage (#120) — a 5e rule (unconscious implies prone; both grant advantage) that existing content reaches but nothing implemented.
  - Deliberately **no condition state, no persistence change, no subsystem**: nothing yet applies a condition to a combatant who is still standing, so the lifecycle state the engine already tracks is the whole of it. `IsIncapacitatedTarget` marks where condition state joins when something first applies one.
  - **Worth knowing now that enemy tactics are generalized (PR #146):** the frozen transcripts did not move when that landed, because `EncounterTacticsPolicy` (renamed from `WatchtowerRaiderPolicy`) only targets conscious combatants. An AI that finishes off downed characters *will* move them.
  - **Spellcasting and feature effects — the design is adopted and all six of its steps are done** (#131–#140). The design doc (`docs/spellcasting-and-feature-effects-design.md`) has been removed now that all six steps are merged; the summary below is what's left of it.
    - **The thing that was actually built is one seam, not a spell system.** `RollContributionRules` asks a combatant what contributes to a named roll and answers with a flat bonus plus **the dice the caller must roll**; a second call totals what the caller then rolled. Two calls rather than one, because collapsing them would put randomness back inside the rules — and because a contribution that adds a d4 changes the roll's *arity*, which is why a roll has to be asked what it needs before it is made. The prerequisite evaluations were already where a caller asks before rolling (`AttackRollMode` has always said whether to roll one d20 or two), so contributions ride there.
    - Steps 1–4 (#132–#136) built the content model, slots as ammunition-shaped persistent resources, and the five spells that force distinct mechanisms. Step 5 split: #137 applied effects and held concentration, **#138 made contributions actually modify rolls** (weapon attack, spell attack, spell save, and `EncounterSavingThrowRules`).
    - **Step 6 (#139–#140) is the one that proves the seam is not spell-shaped, and it is worth knowing what it cost.** Sneak Attack needed three things Bless did not: contributions arriving from `EncounterCombatProfile.Contributions` rather than an `ActiveEffect` (a feature is not something that happened to you and does not expire); `RollContributionTarget.DamageRoll`, which rides on `EncounterWeaponAttackEvaluation` rather than the prerequisites **because a miss deals no damage for anything to contribute to** — so unlike the attack roll, that arity is only knowable after the roll it depends on; and conditions. Nothing in the spell path changed.
    - **`Conditions` is an AND-list and deliberately not an expression language.** 5e's one disjunction — advantage, or a crowded target, and no disadvantage either way — is a *single named condition* (`AdvantageOrAdjacentEnemy`), because that is what it is in the rulebook. Don't grow a condition tree for the two features that would use it.
    - **`FeatureDefinition` woke up `ClassDefinition.FeaturesByLevel`**, which had held inert strings since the beginning. Feature IDs now have to resolve, for class *and* background features alike — one rule, because an arbitrary split is what somebody trips on. **A feature contributing nothing is allowed, unlike an effect:** an effect that changes nothing is nothing, but a feature that changes nothing is one whose resource and action legs are not built yet, which is exactly where Second Wind will sit. Don't tighten that without building those legs.
    - **Both frozen transcripts survived all six steps untouched**, because a combatant with no effects and no profile contributions asks for no dice, so the sequence is byte-identical. They move the first time someone in the Watchtower fight is blessed or is a rogue — correct behaviour when it happens, and a deliberate reviewed regeneration.
    - **Known gaps, deliberately left:** once-per-turn is not enforced on Sneak Attack, and cannot be violated at level one (no Extra Attack, no bonus-action attack, and an opportunity attack is on somebody else's turn — which 5e allows anyway); the check joins when Extra Attack does. **Confirmed 2026-07-28: the party stays level 1 for now, and there is no leveling system planned.** Extra Attack is a 5th-level Fighter feature, so this isn't a "build it next" gap — it's indefinitely out of reach until leveling itself is built, and building Extra Attack ahead of that would be mechanics with no content that could ever need them. Don't pick this up without a leveling system landing first. ~~Nothing counts `ActiveEffect.RemainingRounds` down, so an effect never expires.~~ — **closed (PR #151).** `EncounterTurnAdvancementRules.Resolve` decrements every active effect once per round (not once per the sustaining caster's turn — this engine has no notion of whose turn started an effect, and ticking every copy of a multi-target effect in lockstep at round start is the simplification the architecture already supports) and clears `ConcentratingOnEffectId` on natural expiry. ~~Concentration checks on taking damage are still unbuilt.~~ — **closed (PR #153).** `EncounterDamageRules.Resolve` — the single place every damage source (weapon or spell) funnels through — now asks for a Constitution save (DC 10 or half the damage, whichever is higher) whenever a concentrating combatant takes damage and stays conscious; a failed save or the damage itself leaving them incapacitated both drop the effect via the `ActiveEffectRules` extracted for it. ~~**Deliberately Core-only, same call as PR #151:** nothing in `FiveEGoldBox.Application` calls `EncounterSpellRules.Resolve` yet...~~ — **spellcasting reached the decision surface (PR #158).** `WatchtowerCombatDecisionFactory` now offers every spell a combatant has prepared, mirroring weapon attacks; a new `EncounterSpellRules.Evaluate` (internal, mirroring `EncounterWeaponAttackRules.Evaluate`) lets `WatchtowerCombatSpellAttackStaging` ask what a cast needs before rolling it. Both effect expiration and concentration checks are consequently reachable in live play now — closing that out required retrofitting concentration-check dice into `WatchtowerCombatAttackStaging` (weapon attacks) too, since a live game could otherwise throw the moment a blessed target took a sword hit. ~~Deliberately single-target only: Bless and Magic Missile's multi-target capability is proven at Core but not exposed on the decision surface...~~ — **Bless side closed (PR #161).** `WatchtowerCombatDecisionFactory`/`CombatViewFactory` now offer every legal combination of two or more targets for a spell with `AppliedEffectId`, and Core needed no changes — `AdditionalTargetCombatantIds` already worked. **Magic Missile stays single-target, and not just as unfinished scope:** `ResolveDamage`/`ResolveHealing` both land their whole total on the single primary target regardless of how many are named, so multi-target selection is gated on `AppliedEffectId` specifically — a damage spell that can't actually split its damage across targets isn't offered the choice. ### Scope decisions governing Phases 9–12 (2026-07-26)

**The Scope Matrix (`docs/supported-scope-matrix.md`, since removed) was the *Accepted baseline*** governing this section, more authoritative than either development plan. Four decisions were taken against it:

1. **The Scope Matrix supersedes Priority 2 Phase 10.** That phase says "wire full mechanical effects for all 15 Conditions"; the baseline commits **Prone** as the only reusable combat condition for the slice, alongside the health/lifecycle states, and `docs/game-development-goals.md` (since removed) said *"do not implement every condition at once — implement the conditions required by current spells, monsters, traps, and environments."* **Mechanics are built when authored content needs them, not ahead of it.** This inverts the plan's Phase 9→10 ordering: content leads.
2. ~~**Encounter construction is generalized; enemy tactics are not.**~~ — **resolved (PR #146).** Any scenario may author and start its own fight, built from its `EncounterDefinition`, and now any scenario's fight can be *driven*: tactics reduced to two structural checks (which side is the party's, which weapon is melee) rather than a Watchtower-specific subsystem, so one implementation now serves both scenarios. `SunkenChapelCombatTests` proves it by playing the chapel's guardian fight to a party victory with zero chapel-specific code in the combat layer. The per-adventure tactical *design* the plan meant to keep explicit — a monster choosing to flee, a caster prioritizing a healer — is still a real future decision; what's resolved is that the plumbing no longer forces every scenario through Watchtower's name.
3. ~~**Godot work is engine-side only.**~~ — **superseded (2026-07-28, PR #170).** The user asked for the two lines to stop developing separately. `AppShell` now runs a real session by default through `RealGameSession` (see Phase 11 above) — the "not wiring `AppShell`" boundary this decision drew is gone for the slice that's wired (outpost/exploration/travel). What's still true: `Application`'s public API stays client-agnostic (nothing there references Godot), and combat integration is deliberately not started — `CombatOperations` is heavier and Godot's tactical UI (M8) doesn't exist yet. Read this as "engine-side only" retired, not "fully integrated."
4. ~~**Party size stays three until the real campaign party is authored.**~~ — **resolved (PR #145).** The roster now fields the baseline's four — Fighter, Rogue, Cleric, Wizard — with Barbarian and Ranger kept as reserve. Both frozen combat transcripts were deliberately regenerated for it.

Test infrastructure (Phase 8) stays an ongoing habit rather than a finished thing — the plan says so, and the useful discipline it leaves behind is: **measure distinct bodies before deduplicating anything**, because declaration counts overstate real duplication by a wide margin in this suite.

**Open constraints, in rough order of when they will bite:**

- ~~**Enemy *tactics* are still Watchtower-specific**~~ — **resolved (PR #146).** See scope decision 2 above. **Left deliberately for later:** the ~30 other `Watchtower*`-prefixed files in `Combat/` (orchestrator, decision factory, session mapper, path search, attack staging, step factory, result mapper, the `Combat*Intent`/`Option`/`Decision` types) are already scenario-agnostic in *behavior* — confirmed by grep, none references a Watchtower-specific identifier — just still cosmetically named for it. Renaming them is real cleanup but large and purely cosmetic; not bundled into #146.
- ~~**No `Campaign` type.**~~ — **built (PR #129).** `CampaignDefinition` owns the roster, active party size, ruleset and scenario list; `CampaignRegistry` resolves one and derives scenario→campaign ownership rather than declaring it twice. All three placeholders are gone: `StartingParties`, `WatchtowerPartyCompositionValidator`, and the roster that lived in `WatchtowerScenarioContent`.
  - **The roster is data.** It was three C# methods building `CharacterDraft` literals; `CharacterDraft` was already a plain record, so they were literals wearing a function. Adding, changing or re-classing a character is now an edit to `FrontierCampaignContent` and nothing else.
  - **Party composition validation runs earlier and asserts differently.** It checks party size against the campaign, roster membership, and that each member matches the build it claims — it no longer counts classes, because the roster says what each character is. Five trigger tests moved from `InvalidOperationException` (deep in character resolution) to `ArgumentException` (session validation) as a result.
  - ~~**Still three characters...**~~ — **resolved (PRs #143–#145).** The roster now fields Fighter/Rogue/Cleric/Wizard, with Barbarian and Ranger kept as reserve. Getting there needed two things nobody had built yet, found while starting the swap: gear for the three unplayed classes (#143 — the Rogue's shortbow is also the first ammunition weapon in the ruleset no ranger owns, closing the ammunition-genericity gap noted under Phase 6 above), and a caster's prepared spells actually reaching the battlefield (#144 — `PreparedSpellIds` had been read by nothing; `SpellAttackResolver` now does for spells what weapon resolution has always done for weapons). The swap itself (#145) deliberately regenerated both frozen transcripts. ~~**Worth knowing:** the baseline party loses the Watchtower fight as authored...~~ — **this claim was wrong, and the actual bug is fixed.** It came from two test drivers that only ever attacked or ended a turn; a party member with no target in reach just passed forever while the raiders' own AI (which does move) closed in and picked characters off. That looked exactly like a losing damage race and was not one — a 1,000-seed simulation against the real, un-nerfed raiders with a driver that chases the nearest reachable target puts the baseline party at a ~96% win rate. Both tests now move, and the raider-HP nerfs (down to 3, and a token 9→8) are gone. Rebalancing the Watchtower encounter is not a real open item.
- ~~**A scenario can still only have one travel route**~~ — **resolved (PR #167).** `RegionalTravelRules.BeginJourney(session, routeId)` picks between multiple routes now; `GetAvailableRoutes` (internal) is the discovery seam, and `SessionView` offers one `BeginJourney` action per available route rather than guessing at a single name for the menu. **Deliberately still scoped, not the full "return journey, fork, choice of approach" list:** only a choice of roads from the scenario's own starting location actually works end-to-end — a route whose origin isn't that location now validates as a legitimate shape but could never be attempted, because nothing transitions the party back into outpost mode once they've left it. `ScenarioDefinitionValidator` catches that explicitly (`scenario.routes.origin_unreachable`) instead of leaving it to fail silently at runtime the way the old blanket "only one route" check used to. A real hub-return transition — what a genuine return journey needs — is separate, larger work, not bundled here.
- **Outpost decisions were hardcoded to a binary accept/decline choice** (`OutpostMissionChoice`) despite `ScenarioDecisionOptionDefinition.OptionId` already being a free-form string in the content model. Found building the Hollow Mill's branch: a scenario declaring a third option would validate fine and then simply never be offered, because `SessionView` filtered every option through `Enum.TryParse<OutpostMissionChoice>`. **Resolved (PR #168):** `OutpostDecisionRules` resolves any number of options purely by their own string ID, the same pattern `BeginJourney(routeId)` established for routes — `OutpostMissionChoice`/`OutpostMissionResult`/`OutpostMissionRules` are gone. Deliberate breaking change to the public API: 64 → 63 exported types, verified by reflection. Hollow Mill's opening decision carries a third option as the proof; the three scenarios' existing options kept their exact string values, so no scenario behavior changed.
- ~~**Mid-journey saving was refused for every scenario alike**~~ (Phase 3's note above still describes mid-*combat* saving correctly — that part is unchanged). **Resolved for travel (PR #169):** the V1 save DTO and `SaveGameMapper` had carried `RegionalTravelState` completely since the format's first version; only `ManualSaveSerializer.IsSaveableMode` excluding `ApplicationMode.RegionalTravel` blocked it. Encounter stays excluded, deliberately — a combat's turn order and mid-resolution rolls aren't comparably simple data, and `SaveActiveEncounterV1` is still the empty placeholder it always was.
- ~~**No scenario declares its ruleset in a resolvable way.**~~ — **resolved (PR #119):** `RulesetRegistry` resolves `ScenarioDefinition.RulesetId`. Both scenarios name the same campaign ruleset rather than inheriting it.

## Workflow authorization for Priority 1 branches

For each Priority 1 branch, proceed autonomously through the full loop without stopping to ask permission at each step:

1. Confirm `git status` clean and `main` in sync with `origin/main`.
2. One narrowly-scoped branch per plan step (see the plan's "Recommended Branch Sequence").
3. Implement.
4. Gate: focused tests → full affected-project tests → full solution build+test → `git diff --check`. Also verify compiled public API counts via reflection (`Assembly.GetExportedTypes()`) when a change could affect visibility — don't trust grep or doc claims for this.
5. Self-review the diff against that phase's completion gate from the plan; report gaps honestly rather than glossing over them.
6. Commit — one commit, message explains what and why. **Do not** write `Priority_1_Phase_*_Assignment_Packet.md`-style docs; that ceremony was for coordinating across disconnected sessions/tools and doesn't apply when working directly in the repo. Put equivalent content in the commit message and PR body.
7. `git add` **specific paths only, never `-A` or `.`** — the repo root has ~50 untracked process-doc/patch/log files (see below) that must never be staged. **`git stash -u` is the same hazard** and is equally off-limits: it lifts the untracked `docs/` assets out of the working tree, and that work is often being edited concurrently. If a clean tree is needed to build a baseline (e.g. the reflection API check against `main`), use `git worktree add` or a copy in a scratch directory instead of stashing.
8. Push, open a PR (`gh pr create`), wait for CI (`gh run watch`), merge (`gh pr merge --merge --delete-branch`) once green.
9. `git fetch --prune`, confirm `main` synced, move to the next branch.

Still pause and flag rather than pushing through: gate failures, merge conflicts, CI failures, or anything that looks destructive/irreversible outside the normal branch→PR→merge flow. This authorization is specific to Priority 1 cohort work in this repo — it doesn't generalize to unrelated pushes, merges, or deletions.
